# [개정] 화질을 전혀 낮추지 않는 원칙으로 다시 정리 (사용자 요청 반영)

## 용량 정정
- **167은 파일 개수**이고, 첫 필드까지 받는 용량은 **약 60MB**다.
- **전체 패키지는 약 782MB**다. 앱 26.9MB + CDN 755.2MB, 1,704개 파일 (DEVELOPMENT_STATE 10/3 기록). 사용자가 받으신 800MB 이상과 같은 규모다.
- 지금 문제는 "첫 필드에 필요한 60MB"가 아니라 **"782MB 전체를 시작할 때 받는 구조"**다.

## 멈춤 원인 (확정/추정 구분, 모두 화질과 무관)

| 순위 | 원인 | 근거 | 화질 손실 없는 해결 |
|---|---|---|---|
| 1 | 영웅·편성 화면을 열 때 **원본 해상도 픽셀 전체를 메인 스레드에서 훑음** (`standingPartySprite.ts` fit + getImageData) | **확정**: 1회 0.4~0.7초. 저사양 조건에서는 1.15초 동안 화면 멈춤 | 윤곽 경계값을 빌드할 때 계산해 JSON으로 넣는다. 화면 결과는 완전히 같다 |
| 2 | 시작할 때 **캐릭터 시트를 실행 중에 다시 잘라 PNG로 재인코딩** (`poc/fieldView.ts:383-415`, 시트당 16프레임) | **확정**: 첫 필드까지 `toBlob` PNG 인코딩 48회 + 다시 디코딩. WebKit에서 이 작업이 메인 스레드를 얼마나 막는지는 **추정** | 프레임을 빌드할 때 미리 잘라 둔다(같은 픽셀). 또는 시트를 그대로 그린다(`?frameImages=0` 경로가 이미 있음) |
| 3 | **풀어 놓은 이미지가 차지하는 메모리** (2560² 시트 1장 ≈ 26MB, 첫 필드의 큰 원화 합계 수백 MB) | **추정**: iOS WebView는 메모리 압박 시 이미지를 버렸다가 다시 풀면서 끊긴다. 초기의 "완전 끊김" 증상과 맞는다. Safari Timelines 메모리 그래프로 확인 필요 | 지금 화면에 필요한 이미지만 풀어 두고, 화면을 벗어나면 해제한다(src 해제, ImageBitmap close). 표시 직전에 `decode()`로 미리 풀어 둔다 |
| 4 | **저장 폭주** (40초에 95회, 상태 전체 14KB를 동기 기록, v2·v3 이중 기록) | **확정**: 횟수·크기. 아이폰에서의 비용은 **추정** | 모아서 늦게 쓰고, 이중 기록을 없앤다. 즉시 저장이 필요한 결제·보상은 예외 |
| 5 | 전투 화면 그리기 비용 | **미확정**: 이 환경은 GPU 없이 측정했다 | 아이폰 Timelines로 확인한 뒤 판단 |

## 용량·로딩: 화질을 낮추지 않는 방법

1. **무손실 압축 (픽셀 완전 동일)**
   - 무손실 WebP 샘플 결과: 원본 대비 59~77% 크기(평균 약 30% 절감). 픽셀 비교 차이 **0개**로 동일함을 확인했다.

   | 파일 | PNG | 무손실 WebP |
   |---|---|---|
   | m1 스프라이트 | 2,470KB | 1,698KB |
   | 웹툰 01 | 1,594KB | 941KB |
   | 타이틀 | 2,532KB | 1,967KB |
   | 재료 아틀라스 | 1,756KB | 1,305KB |

   - 전체 782MB → 약 550MB (추정)
   - 무손실 PNG 재압축(oxipng 등)만 해도 일부 줄어든다. 이것도 픽셀 동일이다.
2. **받는 시점 나누기 (화질 그대로)**
   - 782MB 전체를 처음에 받지 않는다.
   - 시작 0단계: 타이틀, 1-1, 시작 3명만 받는다. 현재 약 60MB이고, 무손실 압축을 하면 약 40MB로 줄어든다(추정).
   - 나머지는 플레이 중 백그라운드로 받거나, 해당 화면에 들어갈 때 받는다.
   - 화질 변화가 전혀 없는 구조 변경이다.
3. **중복 다운로드와 캐시**
   - 같은 파일을 두 번 받지 않도록 한다. 지금은 타이틀과 웹툰을 각각 2회 받고 있다.
   - 파일 이름에 해시를 붙이고 1년 캐시를 적용한다. 두 번째 실행부터는 0MB를 받는다.
4. **[선택, 사용자 판단] 화면 해상도 기준으로 크기 조정**
   - 측정 결과: 640px 캐릭터 프레임은 실제로 **약 192~209 기기 픽셀**로 그려진다. 캔버스는 DPR 2로 제한되어 있다.
   - 원본은 실제 표시 크기보다 3배 이상 크다.
   - 프레임을 320px로 줄여도 표시 크기의 1.5배 이상이라 이론상 화면에서는 차이가 없다.
   - 이 안을 적용하려면 줄이기 전·후의 실제 게임 화면 픽셀 차이를 측정해, 눈으로 구분할 수 없다는 근거를 먼저 제시한다. 사용자가 승인한 경우에만 적용한다. 원본 원화는 그대로 보관한다.

## 결론
- **끊김 원인 1·2·4는 화질과 전혀 상관없는 코드 문제**다. 고쳐도 화면 결과는 바이트 단위까지 같다.
- 원인 3은 이미지를 언제 풀어 두고 언제 놓을지의 관리 문제다. 화질과는 관계없다.
- 용량은 무손실 압축과 나눠 받기만으로 줄인다. 손실 압축과 해상도 축소는 기본안에서 뺐다.

# iOS 끊김 테스트와 CDN·초기 로딩 방안 (기준 2e04f7f)

## 0. 측정 조건과 한계
- **실제 아이폰으로는 측정하지 못했다.** 이 환경에는 Chromium만 있고 WebKit/iOS는 없다.
- 대신 로컬에서 다음 조건으로 측정했다.
  - Chromium, 모바일 390×844, DPR 3, 터치
  - 저사양 폰을 흉내 내려고 CPU를 4배 느리게 함
  - 첫 실행부터 1-1 필드까지 진행, 공용 주소는 사용하지 않음
- 아래 수치는 **원인 후보를 좁히기 위한 대리 측정**이다. 아이폰에서의 실제 프레임 수치는 4장 방법으로 확인해야 한다.
- 표시 규칙: 코드를 읽거나 측정해서 확인한 것은 **확정**, 아이폰에서 같은 일이 생길 것이라는 판단은 **추정**으로 적는다.

## 1. 끊김 원인 후보

### 1-1. [확정] 영웅·편성 화면을 열 때 메인 스레드가 0.4~0.7초 멈춤
- **위치:** `ui/dom/standingPartySprite.ts:8-22`의 `fit()`
- **하는 일:** 영웅 원화를 원본 해상도 그대로 캔버스에 그린다. 그다음 `getImageData`로 모든 픽셀을 한 개씩 훑어 투명하지 않은 영역의 경계를 계산한다. 영웅 1명마다 이 작업을 한다.
- **측정:**
  - 영웅 화면 1회 열기에 `fit` 384ms + `getImageData` 285ms가 걸림 (CPU 정상 속도 기준)
  - CPU 4배 저하 조건에서는 한 번에 1.15초짜리 긴 작업이 생김
- **아이폰 (추정):** WebKit에서 `getImageData`를 쓰면 GPU에 있는 이미지를 CPU로 다시 읽어 와야 해서 더 느리다. "가이드 버튼을 누르는 등 동작할 때 끊긴다"는 증상과 맞는다. 영웅 화면, 편성 화면, 가이드로 영웅 화면에 들어갈 때마다 발생한다.
- **수정:**
  - 실루엣 경계값을 **빌드할 때 미리 계산해 JSON으로 저장**하고, 게임 중에는 읽기만 한다. 효과가 가장 크다.
  - 당장 고치려면 원본 대신 128px로 줄인 캔버스에서 계산한다. 비용이 약 1/100로 줄어든다.

### 1-2. [확정] 가이드 버튼 탭·보상 확인 시 긴 작업 발생, 진행 중 저장이 잦음
- **측정 (CPU 4배 저하):**
  - 가이드 독을 누를 때 543ms짜리 긴 작업 발생
  - 확인 버튼을 누른 뒤 3초 동안 저장 12회, 저장 데이터 164KB
- **저장 방식:** `GameStore.save()`(`state/gameState.ts:2486`)가 상태 전체(약 14KB)를 JSON으로 바꿔 localStorage에 동기로 기록한다.
  - 약 40초 플레이 동안 95회 저장
  - 전투 중에도 처치할 때마다 저장
  - 저장 키가 두 개(v2·v3)라 같은 내용을 두 번 기록함
- **아이폰 (추정):** WKWebView의 localStorage 쓰기는 디스크 I/O를 동반하는 동기 처리라 기기에 따라 1회 수~수십 ms가 걸릴 수 있다. 버튼 처리와 저장이 같은 프레임에서 일어나면 탭할 때 끊김으로 느껴진다.
- **수정:**
  - 저장을 **모아서 늦게 쓰기**로 바꾼다. 변경이 생기면 표시만 해 두고, 300~500ms 안에 한 번 또는 화면 전환·앱 백그라운드 전환 때 기록한다. 결제·보상 수령처럼 즉시 저장이 필요한 것은 예외로 둔다.
  - v2·v3 이중 기록을 정리한다.
  - 전투 처치마다 하던 저장은 몇 초 간격으로 묶는다.

### 1-3. [확정] 첫 필드까지 이미지 약 60MB, 큰 원화를 그대로 사용
- **측정:**

| 시점 | 경과 | 요청 수 | 받은 용량 |
|---|---|---|---|
| 타이틀 | 3.2초 | 109개 | 7.0MB |
| 1-1 필드 | 13.0초 | 167개 | **59.5MB** (PNG가 59.1MB) |
| 필드 진입 후 30초 | 43.0초 | 182개 | 63.2MB |

  - 이 수치는 로컬 서버 기준이라 네트워크 대기 시간이 없다. 휴대폰 망에서는 훨씬 길어진다.
- **원화 크기:**
  - 파티 캐릭터 스프라이트(`battle/field-poc/m1·m3·m5·guard·archer-v1.png`)가 각각 **2560×2560 PNG, 약 2MB**다.
  - 화면에서는 캐릭터가 수십~100px 크기로 그려지는데, 원본은 이보다 훨씬 크다.
- **중복 다운로드:** 타이틀 원화와 웹툰 페이지가 **두 번씩 받아짐**. 미리 받기(preload) 후 실제 `<img>`가 다시 요청한다.
  - 개발 서버는 캐시를 쓰지 않아서 생긴 것일 수 있다. 실제 CDN 캐시 헤더에서도 같은지 확인해야 한다.
- **아이폰 (추정):** 2560² 이미지는 화면에 쓰려고 풀어 놓으면 1장당 약 26MB 메모리를 차지한다. 첫 필드의 큰 원화만 합쳐도 이미지 메모리가 수백 MB가 된다. 이런 경우 WebKit은 메모리 압박으로 이미지를 버렸다가 다시 풀게 되고, 처음 그릴 때마다 디코딩이 일어나 끊긴다. 초기에 "완전히 끊기던" 증상과 맞는다.

### 1-4. [측정 한계] 전투 화면 자체의 프레임
- CPU 4배 저하 조건에서 전투 화면 프레임이 100~170ms(약 6~10fps)였다. 같은 조건에서 소환 화면(전투 정지)은 17ms였다.
- 다만 측정한 시간의 69%가 그리기·합성이고 게임 로직(JS)은 약 25%다. 이 측정 환경은 GPU 없이 소프트웨어로 그리기 때문에, 이 수치를 아이폰에 그대로 적용할 수는 없다.
- 캔버스 해상도는 이미 DPR 최대 2로 제한되어 있다(`poc/fieldView.ts:109`).
- 아이폰에서는 4장의 실기기 측정으로 확인해야 한다. 큰 스프라이트를 줄이는 것(1-3)이 그리기 비용에도 직접 도움이 된다.

## 2. CDN·초기 로딩 방안

### 현재 상태 (DEVELOPMENT_STATE.md 10/2~10/3 기록과 이번 측정)
- 전체 파일: 앱 패키지 26.9MB + CDN 755MB, 1,704개
- 시작할 때 화면을 막고 받는 파일(`fieldRenewal.ts:70`): 웹툰 6장, 파티 원화·로비 이미지·필드 스프라이트 등. 이것만으로 수십 MB다.
- 그 결과 "초반 로딩 때 다 받기" 방식이 오래 걸린다.

### 추천: "줄이기 + 3단계로 나눠 받기"

**1) 먼저 파일 크기를 줄인다 (효과가 가장 큼)**
- **WebP로 변환:** 아이폰은 iOS 14부터 WebP를 지원한다. 샘플 측정 결과는 아래와 같다.

| 파일 | 원본 PNG | WebP (품질 82) | WebP + 해상도 절반 |
|---|---|---|---|
| m1 스프라이트 (2560²) | 2,470KB | 345KB | 118KB |
| 웹툰 01 | 1,594KB | 62KB | 26KB |
| 타이틀 원화 | 2,532KB | 212KB | 90KB |
| 재료 아틀라스 | 1,756KB | 370KB | 108KB |

- **해상도 조정:** 스프라이트는 실제로 그려지는 크기의 2배까지만 남기고 줄인다. 2560²는 과하다.
- **예상 효과 (추정):** 첫 필드까지 받는 용량이 약 60MB에서 **약 5~8MB**로 줄어든다.
- **주의:**
  - 화질 손상은 원화별로 눈으로 확인해야 한다. 특히 웹툰 글자와 캐릭터 외곽선을 본다.
  - 원본 원화 파일은 그대로 두고, 빌드 단계에서 변환한 파일만 배포한다.

**2) 3단계로 나눠 받는다**

| 단계 | 내용 | 받는 방식 | 목표 |
|---|---|---|---|
| 0단계 (앱 패키지 포함) | 타이틀, 폰트, UI 아이콘, 1-1 필드 맵, 시작 3명 스프라이트, 웹툰 1~2장 | 앱과 함께 설치, 로딩 화면 없음 | 타이틀 1초 안, 필드 진입 전 대기 0초 |
| 1단계 (뒤에서 받기) | 웹툰 나머지 장, 1-1~1-6 적, 궁수냥, 초보 모집 3명 초상, 소환 연출 | 프롤로그와 1-1 진행 중에 하나씩 백그라운드로 받음. 화면을 막지 않음 | 1-6 도착 전 완료 |
| 2단계 (필요할 때) | 나머지 영웅·던전·이벤트·2장 이후 지역 | 화면에 들어갈 때 받음. 받는 동안 대체 이미지 표시. 다음 장 지역은 쉬는 시간에 미리 받음 | 화면 진입 후 1초 안 표시 |

- 시작 로딩 화면(`prepareStartupAssets`)은 **0단계 파일 검사용으로만** 남긴다. 웹툰 6장 전체를 미리 받는 부분은 빼고, 다음 장은 앞 장을 보는 동안 받는다.

**3) 캐시**
- 파일 이름에 내용 해시를 붙인다(예: `m1-v1.3f2a.webp`). CDN 응답에는 `Cache-Control: public, max-age=31536000, immutable`을 준다. 두 번째 실행부터는 다시 받지 않는다.
- 미리 받은 파일과 실제 `<img>`가 같은 주소·같은 캐시 정책을 쓰는지 확인한다. 이번 측정에서 보인 중복 다운로드를 없애기 위해서다.
- 토스 미니앱 WebView에서 Service Worker나 Cache Storage를 쓸 수 있는지는 **확인이 필요하다**. 쓸 수 없다면 HTTP 캐시만으로 충분하다.

**4) 완료 기준**
- 4G 환경에서 다음을 만족해야 한다.
  - 타이틀까지 3MB 이하
  - 1-1 필드까지 10MB 이하
  - 첫 터치 가능까지 5초 이하
- 1-6까지 화면을 막는 로딩이 0회여야 한다.

## 3. Codex 작업 순서 제안
1. `standingPartySprite` 경계값을 빌드할 때 미리 계산하도록 바꾼다. 작은 수정으로 끊김 체감을 크게 줄일 수 있다.
2. 저장을 모아서 늦게 쓰도록 바꾸고, v2·v3 이중 기록을 정리한다.
3. 빌드 단계에서 WebP 변환과 스프라이트 해상도 조정을 넣는다. 원본은 그대로 두고, 화질 확인용 비교 캡처를 첨부한다.
4. 시작 로딩을 0/1/2단계로 나누고 캐시 헤더와 해시 파일명을 적용한다.
5. 각 단계마다 아래 4장 기준으로 아이폰 실기기 측정 결과를 첨부한다.

## 4. 아이폰 실기기 측정 방법 (사용자 또는 Codex가 실행)
1. Mac의 Safari와 아이폰을 연결한다. 아이폰 설정에서 '설정 > Safari > 고급 > 웹 속성'을 켠다.
2. 토스 앱 대신 같은 배포 주소를 아이폰 Safari로 연다. 토스 WebView에서 웹 검사가 가능하면 그쪽에서 측정한다.
3. Safari 개발자 메뉴 → 기기 → 페이지 → **Timelines** 녹화를 시작한 뒤 아래 순서로 진행한다.
   - 처음 실행
   - 1-1 필드 진입
   - 가이드 버튼 3회
   - 영웅 화면 열기
   - 보상 확인
4. 기록할 것:
   - 50ms 넘는 JS 작업 목록과 함수 이름
   - 프레임 수 (전투 중 평균, 버튼 누른 직후 최저)
   - 메모리 그래프의 최대치
   - 네트워크 탭의 총 용량과 받은 시간
5. 수정 전·후를 같은 기기, 같은 순서로 비교한다. 측정 기기는 가능하면 구형(iPhone 11 이하) 1대와 최신 1대로 한다.
