# iOS 끊김·로딩 개선 — Codex 전달 명세 (기준 2e04f7f)

## 원칙
- **화질 손실 0.** 원본 원화는 수정하거나 삭제하지 않는다. 손실 압축과 해상도 축소는 하지 않는다.
- 화면 결과가 바뀌면 안 된다. 수정 전과 후의 같은 화면 캡처는 픽셀이 같아야 한다. 애니메이션 타이밍 차이는 허용한다.
- 각 단계마다 아래 '측정'을 수정 전과 후로 첨부한다.

## 1단계: 멈춤 원인 제거 (코드만 수정, 화질 영향 없음)

### 1-1. 영웅·편성 화면 열 때 멈춤 [확정, 최우선]
- 위치: `ui/dom/standingPartySprite.ts:8-22` `fit()`
- 현재 동작: 원본 해상도 이미지를 캔버스에 그리고, `getImageData`로 받은 모든 픽셀을 메인 스레드에서 순회해 실루엣 경계를 계산한다.
- 측정값:
  - 영웅 화면 1회 열 때 `fit` 384ms + `getImageData` 285ms
  - CPU 4배 저하 조건에서는 1.15초 동안 화면이 멈춤
- 수정:
  - 빌드 스크립트에서 영웅별 경계값 `{left,right,top,bottom,w,h}`을 계산해 `data/silhouetteBounds.json`에 넣는다.
  - `fit()`은 이 값을 읽기만 한다.
  - 표에 없는 영웅이 나오면 원본을 128px 이하로 줄인 캔버스에서 계산하는 경로를 남긴다.
- 검수: 영웅 화면과 편성 화면의 캡처가 수정 전과 픽셀 단위로 같아야 한다.

### 1-2. 시작 시 스프라이트 프레임 재인코딩 [확정]
- 위치: `poc/fieldView.ts:383-415` `loadStarterSprite`. 기본으로 켜져 있음(`frameImages` 파라미터, `:118`).
- 현재 동작: 2560×2560 시트를 640px 프레임 16개로 잘라 `toBlob('image/png')`로 다시 인코딩하고 다시 디코딩한다. 1-1 필드에 들어갈 때까지 48회 발생한다.
- 수정 (둘 중 하나):
  - (a) 빌드 단계에서 프레임 파일 16개를 미리 잘라 둔다. 원본 픽셀을 그대로 복사하고 무손실로 저장한다.
  - (b) 프레임 분리를 없애고 시트에서 바로 `drawImage(시트, 소스 좌표…)`로 그린다. 이미 있는 `?frameImages=0` 경로를 기본으로 만든다.
- (b)를 고를 경우, (b)가 원래 왜 꺼졌는지 기록을 확인하고 이유를 남긴다. iOS 메모리 대응이었을 수 있다.

### 1-3. 저장이 너무 잦음 [확정]
- 위치: `state/gameState.ts:2486` `save()`
- 측정값:
  - 약 40초에 95회 저장
  - 매번 약 14KB JSON을 localStorage에 동기 기록
  - `sangukni_save_v2_*`, `sangukni_save_v3_*` 두 키에 같은 내용을 이중 기록
- 수정:
  - `save()`를 '저장 예약'으로 바꾼다. 변경 표시를 해 두고 400ms 안에 1회만 기록한다.
  - 다음 경우에는 즉시 기록한다:
    - `visibilitychange(hidden)`, `pagehide`
    - 화면 전환
    - 결제 처리(`paymentCommit`, `grantIap`)
    - 보상 수령 확정
  - v2·v3 이중 기록을 정리한다. 마이그레이션 완료 후에는 한 키만 쓴다. 구 키를 읽는 경로는 유지한다.
  - 전투 처치 때마다 하던 저장은 5초에 1회로 묶는다.
- 검수:
  - 기존 저장·복구·결제 테스트가 모두 통과해야 한다.
  - '앱 강제 종료 직전 저장'을 시뮬레이션하는 테스트를 추가한다.

### 1-4. 이미지 디코딩과 메모리 [추정, 아이폰 측정으로 확정]
- 현재 상태:
  - 2560² 시트를 디코딩하면 1장에 약 26MB.
  - 첫 필드에 큰 원화가 많아서, 디코딩된 이미지 합계가 수백 MB가 될 수 있다.
- 수정:
  - 화면에 새 이미지를 보여 주기 전에 `img.decode()`나 `createImageBitmap`을 끝내 둔다. 첫 표시 프레임에서 디코딩하지 않게 한다.
  - 화면(모달)을 닫으면 그 화면에서만 쓴 큰 이미지는 `src`를 해제하거나 `ImageBitmap.close()`로 놓아준다.
  - 웹툰은 보고 있는 장과 다음 장만 메모리에 둔다.

## 2단계: 용량·로딩 (화질 동일)

### 2-1. 무손실 압축
- 빌드 단계에서 PNG를 **무손실 WebP**로 변환해 배포한다(`webp:lossless`, method 6). 원본 PNG는 저장소에 그대로 둔다.
- 샘플 4개 측정 결과, 원본 대비 59~77% 크기였고 픽셀 차이는 0이었다.
  - m1 스프라이트 2,470KB → 1,698KB
  - 웹툰 01 1,594KB → 941KB
- 변환한 파일 전체를 대상으로 원본과 픽셀이 같은지(차이 0)를 자동으로 검사한다.
- WebP를 지원하지 않는 환경을 위해 PNG도 함께 둔다. iOS 14 미만이 대상이다.

### 2-2. 나눠 받기
- 현재 상태:
  - 전체 약 782MB (앱 26.9MB + CDN 755MB, 1,704개 파일)
  - 1-1 필드에 들어가기까지 167개 파일, 약 60MB를 받는다.
- 0단계 (시작 전 필수): 타이틀, 폰트, UI 아이콘, 1-1 맵, 시작 3명 스프라이트, 웹툰 1장
- 1단계 (백그라운드): 웹툰 나머지 장, 1-1~1-6의 적·궁수냥·초보 모집 3명·소환 연출. 프롤로그와 1-1을 진행하는 동안 화면을 막지 않고 받는다.
- 2단계 (필요할 때): 나머지 전부. 해당 화면에 들어갈 때 받고, 받는 동안 대체 표시를 보여 준다. 다음 장에 쓸 것은 쉬는 시간에 미리 받는다.
- `fieldRenewal.ts:70` `prepareStartupAssets`에는 0단계 목록만 넘긴다.

### 2-3. 중복 다운로드와 캐시
- 로컬 측정에서 같은 파일을 2번씩 요청하는 경우가 있다. 타이틀 원화와 웹툰 페이지다.
  - 미리 받은 파일을 같은 `Image` 객체나 같은 URL·캐시 정책으로 다시 쓰게 고친다.
  - CDN 실제 응답 헤더로 다시 확인한다.
- 파일 이름에 내용 해시를 붙이고 `Cache-Control: public, max-age=31536000, immutable`을 적용한다.

## 3단계: 아이폰 측정 도구 보강 (사용자가 아이폰에서 직접 측정)
- 이미 있는 `?perf=1` 오버레이(`poc/fieldView.ts:144-155, 906`, `poc/deviceFrameTrace.ts`)에 아래를 추가한다.
  - 버튼·가이드를 누른 시점부터 다음 프레임까지 걸린 시간. 최근 10건을 "탭 지연 N ms"로 표시한다.
  - 50ms를 넘는 작업이 생기면 어느 단계에서 생겼는지 표시한다(`traceCost` 표식 활용). 대상: 저장, 영웅 화면 생성, 보상 팝업, 이미지 디코딩.
  - JS 메모리 사용량. 지원하는 경우에만 표시한다.
  - 지금까지 받은 이미지 개수와 용량.
  - **[결과 복사] 버튼**: 측정 결과 JSON을 클립보드에 복사한다. 사용자가 그대로 붙여 넣어 전달할 수 있게 한다.
- `?perf=1`은 `?onboarding=qa`와 함께 쓸 수 있어야 한다. 실제 플레이 저장 데이터와 분리되도록 한다.

## 측정 (각 단계 전후, 같은 기기·같은 순서)
1. 아이폰 Safari나 토스 앱에서 `배포주소/?onboarding=qa&perf=1`을 연다.
2. 진행 순서:
   - 시작 → 프롤로그 → 1-1 필드 진입 (시작 시각부터 첫 터치 가능까지 시간을 잰다)
   - 가이드 버튼 3회
   - 영웅 화면 열기 → 레벨업 → 전투로 복귀
   - 보상 확인 3회
   - 소환 화면 열기
   - 2분 동안 전투 그대로 두기
3. [결과 복사]로 JSON을 받는다. 대상 기기는 구형(iPhone 11 이하) 1대와 최신 1대다.
4. 완료 기준 (구형 기기):
   - 탭 지연 최대 100ms 이하
   - 50ms 넘는 작업이 버튼 1회당 0~1건
   - 전투 평균 50fps 이상
   - 1-1까지 받는 용량 40MB 이하, 첫 터치 가능까지 10초 이하 (4G 기준)
